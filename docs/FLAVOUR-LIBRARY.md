# Flavour library

The editor now uses readable **Flavour profile**, **Cooking technique** and
**Breakfast format** selectors. Technical IDs remain internal references.

## Use it

In the recipe editor, choose an optional **Cuisine or style**, search by name,
ingredient or taste, then select a particular combination. The preview shows its
key ingredients, taste tags, applications and guidance. Changing search/style
filters never changes the selected profile. A selected item outside the filter
remains visible as the current selection.

There are 24 built-in reference combinations covering Chinese-, Japanese-,
Korean-, Indian-, Mediterranean-, Italian- and French-inspired directions, plus
cross-style and sweet-breakfast collections. Profiles can have multiple styles;
these tags are browsing aids, not mutually exclusive cuisines or authenticity
claims. No flags or national-cuisine-as-one-flavour classification is used.

**Selecting a profile changes only the recipe's `flavor` reference.** It does not
insert seasonings, replace ingredients, change quantities, create portions, modify
instructions, or approve a remix. A technique/format selection likewise changes
only its descriptive field. Actual recipe edits still go through recipe validation,
version history, authored portion review and existing remix re-review rules.

Open **Preferences → Manage flavour combinations** to browse the library and
create, copy or edit a personal combination. Creation is also available inline in
the recipe editor, without leaving its unsaved draft. Names generate internal IDs
automatically. Save/cancel the inline flavour draft before saving the recipe.

New profiles can reference selected ingredients already in the kitchen catalogue.
**Other seasoning names** are explicitly label-only guidance; they do not create
ingredient records. Some built-in references point to ingredients not yet imported
into a kitchen; they retain an authored readable label. Profile reference lists
are neither exhaustive ingredient declarations nor input to allergen/exclusion
checks. Discovery continues to check the actual recipe ingredients recursively.

Built-ins are read-only; use **Make my own version**. Personal profiles support
revision-protected edits. Use a new combination for a materially different flavour
identity, instead of redefining an existing name. Editing profile guidance does
not edit or approve the recipes referring to it. Profiles cannot be deleted in
this first version, avoiding dangling references. The browser explicitly reports
stale edits and offers a confirmed reload; failed saves retain the local draft.

## Compatibility

Recipes still use schemaVersion 1 with string `flavor` and `method` fields. There
is no new required recipe property or foreign key. Existing catalogue import files
continue to work unchanged. Unrecognised flavour/technique IDs are preserved and
shown as custom/imported options. **Describe this imported profile** creates a
library record for its existing ID; it does not rewrite a recipe or favourite.

Library names are current display annotations. A saved recipe still retains its
exact profile ID, ingredients, quantities and instructions, but a personal profile's
current display name/description is not itself snapshotted into older recipes.
Unknown IDs have a readable fallback. A library request failure shows a retry/error
in the editor and library; it does not fabricate fallback preset data.

Recipe discovery and remix identity remain based on the specific profile ID, not
its cuisine tags. Profiles don't establish that two recipes are compatible; explicit
reviewed, version-pinned remix connections are still required.

## Storage and upgrade

- `lib/kitchen/flavors.ts`: pure types, validation, style/search vocabulary and
  technique/format choices.
- `lib/kitchen/flavor-api.ts`: authenticated, revision-protected profile storage.
- `components/kitchen/flavor-*`: context, selector/preview, form and library.
- `examples/flavor-profiles.json`: authored seed source, verified against the SQL
  seed by tests. Not an application fallback and not a recipe-import pack.
- `0006_flavor_profiles.sql`: generated by the repository's pinned Drizzle Kit;
  creates only `kitchen_flavor_profiles`.
- `0007_seed_flavor_profiles.sql`: Drizzle Kit custom migration; inserts the 24
  built-ins without overwriting an existing profile. No recipe, ingredient,
  favourite, preference, session or remix row is changed.

Both journal entries and snapshots were generated with the existing config and
Drizzle Kit 0.31.10. Existing migration files/baseline/triggers stay unchanged.
Wrangler remains the only migration runner. On the feature checkout, preserving
all local secrets, configuration and database state:

```sh
npm ci
npm run db:migrations:check
npm run db:migrate:local
npm run dev
```

No separate catalogue import is needed for the flavour presets. The above migration
command changes only the local database, not a deployed instance. For a deployed
kitchen, back up the intended D1, review/list the pending remote migrations and
apply them deliberately **before merging** code that the existing main-branch
workflow will deploy. Neither an application request nor CI runs remote migrations.
No new secret, environment variable or dependency is required.

## API

All routes use the existing private access, same-origin cookie mutation checks,
128 KiB body limit and no-store responses. They are not public publishing endpoints.

| Route | Contract |
| --- | --- |
| GET `/api/flavor-profiles` | `limit=1..100`, `after=id`; `{items,nextAfter}`. Unsupported/repeated filters rejected. |
| POST `/api/flavor-profiles` | `{profile,id?}`. Missing ID generates `custom-<UUID>`; explicit IDs support legacy descriptions. Always creates `origin=custom`; existing ID returns 409. |
| GET `/api/flavor-profiles/:id` | `{id,origin,revision,profile}` with ETag. |
| PUT `/api/flavor-profiles/:id` | Complete profile document, If-Match required. Custom profiles only; stale writes return 412. |

A profile has name, description, styles, tasteTags, keyIngredients, applications and
usage. Key ingredients contain `name` and nullable `ingredientId`; explicit IDs in
user writes must exist. Applications are dressing, glaze, marinade, dry-seasoning,
cooked-sauce or finishing-mixture. No quantities or recipe steps are accepted.
The browser paginates the library and explicitly errors beyond 2,000 profiles,
never presenting a truncated library as complete.

## Checks and limits

Run typecheck, lint, Node tests, migration checks, the isolated migration-upgrade
runner, the Worker build/dry run and browser tests. The new coverage includes
fresh/populated migrations, seeded profile parity, all style categories, legacy
IDs, exclusions still using actual recipes, custom CRUD, unknown references,
ETags, selection without ingredient mutation, reloads, session-expired drafts,
conflict recovery and 320/390/1360px layouts.

The feature does not implement automatic seasoning insertion, recipe generation,
public sharing, arbitrary user-defined cuisine categories, flavour deletion,
profile import/export, or new cooking-method catalogue management. Those are
separate changes. Recipes and reference combinations are not kitchen-tested.
